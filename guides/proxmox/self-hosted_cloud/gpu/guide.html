GPU as a Service — RTX 3060 Ti

One driver install on the Proxmox host; nvidia-container-toolkit injects the GPU into both the Jellyfin LXC and the Immich (Docker) LXC · Route B · References gathered 2026-10-05

Chosen route nvidia-container-toolkit

The model: the host installs the NVIDIA driver once and owns the kernel modules. The toolkit injects the user-space driver libraries and /dev/nvidia* device nodes into containers on demand. No driver-version matching between host and each container, no driver reinstall inside LXCs on host upgrades.

End-to-end walkthrough (host driver + toolkit + Docker runtime configuration, written for Docker-in-LXC): digitalspaceport.com — Proxmox LXC Docker GPU passthrough setup guide

Host driver install on PVE 9.2 / trixie / kernel 7.x (current, June 2026): geekistheway.com — Installing latest NVIDIA driver on Proxmox 9.2. Prefer this over older guides — it covers the kernel-7.x specifics below.

Host install corrections learned 2026-10-07 (on cyberpower)

  • Older guides say pve-headers — renamed to proxmox-headers in PVE 9. Use proxmox-headers-$(uname -r). Also install dkms explicitly.
  • Debian 13 (trixie) removed software-properties-common entirely — no add-apt-repository either. Any guide step using them must be replaced with a direct /etc/apt/sources.list.d/*.sources edit.
  • update-initramfs is a command, not a package — run it as its own step after the install.
  • If apt upgrade pulls a new kernel: reboot BEFORE installing the NVIDIA driver, so DKMS compiles against the kernel that will actually boot.

Secure Boot signing + MOK enrollment (done 2026-10-07)

cyberpower boots with Secure Boot ENABLED (consumer board, default keys). The .run installer generated a signing key pair in /usr/share/nvidia/ (nvidia-modsign-key-C0EB95B1.key / nvidia-modsign-crt-C0EB95B1.der) and signed all five modules. DKMS signing was wired manually in /etc/dkms/framework.conf: sign_file=/usr/src/linux-headers-${kernelver}/scripts/sign-file + mok_signing_key / mok_certificate pointing at that pair (verified end-to-end with dkms build/install --force then modinfo | grep signer).

Enrollment flow: mokutil --import <crt.der> (one-time password) → reboot → blue MOK screen → Enroll MOK (NOT "Enroll key from disk") → select the pending key (shown as its EFI device path, e.g. PciRoot...) → Yes → password → reboot. Two failure modes learned: (1) the machine is 500+ miles away, enrollment needs ANYONE at the console for 5 minutes, guided by phone; (2) navigating into the disk file browser (memtest/grub/vmlinuz listing) is the wrong path — back out to the main menu and use Enroll MOK. A password typo silently fails enrollment (module loads with "Loading of module with unavailable key is rejected" in dmesg). Verified: mokutil --test-key says enrolled, nvidia-smi green.

Key details (installer output, for the record): cert /usr/share/nvidia/nvidia-modsign-crt-C0EB95B1.der, SHA1 fingerprint C0:EB:95:B1:A0:E4:E4:2A:62:6E:0D:CF:21:3F:EF:C5:AD:92:A5:EE; private key /usr/share/nvidia/nvidia-modsign-key-C0EB95B1.key. Once enrolled, the same pair signs all future module rebuilds with no re-enrollment needed. Precautions on the private key: it's root-readable in /usr/share/nvidia/; don't loosen permissions on it, and if the box is ever decommissioned, remove the key files.

Device nodes after a clean boot (accept criteria):

  • crw-rw-rw- root 195,0 /dev/nvidia0
  • crw-rw-rw- root 195,255 /dev/nvidiactl
  • crw-rw-rw- root 511,0 /dev/nvidia-uvm
  • crw-rw-rw- root 511,1 /dev/nvidia-uvm-tools

If these are missing after boot, run nvidia-modprobe -c0 -u (and wire it as the LXC pre-start hook later — the containers depend on these nodes existing).

Installing nvidia-container-toolkit (the missing download step)

None of the walkthroughs above cover the install itself. Official NVIDIA procedure (docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html). On the host:

  • curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
  • curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' > /etc/apt/sources.list.d/nvidia-container-toolkit.list
  • apt update && apt install -y nvidia-container-toolkit
  • Verify: nvidia-ctk --version

Inside the Immich (Docker) LXC, repeat the repo + install, then nvidia-ctk runtime configure --runtime=docker and systemctl restart docker. No daemon exists for this toolkit — it's tools + the LXC/Docker hook glue. (For the raw Jellyfin LXC, no Docker runtime config is needed; the LXC hook lines in the next card do the injection.)

Known NVIDIA issue worth knowing: with systemd cgroup drivers, containers can lose GPU access after systemctl daemon-reload (troubleshooting doc on the NVIDIA site).

Wiring the toolkit into an LXC (not just Docker)

The toolkit's LXC hook mounts the driver + binaries into the container at start. Key lines for /etc/pve/lxc/<vmid>.conf plus the PVE 9-specific fixes and debugging: forum.proxmox.com — PVE 9 nvidia-container-toolkit thread

Typical shape (verify against the thread):

  • lxc.hook.mount: /usr/share/lxc/hooks/nvidia
  • lxc.environment: NVIDIA_VISIBLE_DEVICES=all
  • lxc.environment: NVIDIA_DRIVER_CAPABILITIES=all (Jellyfin needs video; Immich ML needs compute)
  • Pre-start hook running nvidia-modprobe so the device nodes exist before the container mounts them

For Docker inside the Immich LXC: nvidia-ctk runtime configure --runtime=docker on the container side, then runtime: nvidia on services that need the GPU.

Alternative route (documented for reference)

Device-node passthrough: pass /dev/nvidia0, nvidiactl, nvidia-uvm, and caps nodes into the LXC and install a matching user-space driver inside it. More commonly documented, but every host driver upgrade must be mirrored inside each container. Forum tutorial: Jellyfin LXC with Nvidia GPU transcoding. Chose the toolkit route instead because it serves both services from one driver install.

Gotchas and notes

PVE 9.x persistence quirk Known failure mode (flagged in the project risk doc): after a host reboot, containers can fail to see the GPU until device nodes are re-created. The nvidia-modprobe pre-start hook in the forum thread is the fix. Test a full reboot after wiring this up — the accept-criteria is a clean nvidia-smi inside both LXCs post-reboot.
Verify driver visibility, not just devices A container can see /dev/nvidia* nodes and still fail if the user-space library version doesn't match the host kernel module version. With the toolkit route the hook handles matching; the failure symptom to recognize is nvidia-smi erroring inside the container while working on the host.
NVENC session cap ~3–5 concurrent NVENC sessions at the driver level. keylase/nvidia-patch lifts it if family-scale transcoding ever saturates.
Unprivileged containers only Never combine this with a privileged LXC. Privileged + GPU passthrough gives container root effective host access.
One GPU, two consumers Jellyfin transcodes and Immich ML share the card. That's fine (driver multiplexes), but a heavy ML re-scan while someone streams 4K can cause transcode stutter. Consider scheduling Immich ML scans off-peak if both ever collide.
